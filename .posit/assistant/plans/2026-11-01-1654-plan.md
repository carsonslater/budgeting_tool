## 2. Data model (m0006)

`goal_allocations`
- `id` INTEGER PK AUTOINCREMENT
- `goal_id` INTEGER NULL REFERENCES goals(id) ON DELETE RESTRICT
- `line_key` TEXT NULL REFERENCES budget_lines(line_key) (verify `line_key` is UNIQUE in m0003)
- `month` TEXT NOT NULL, CHECK `YYYY-MM`
- `kind` TEXT NOT NULL CHECK IN (`sweep`, `withdrawal`, `reserve`, `draw`, `opening`, `reversal`)
- `amount` REAL NOT NULL, signed (see sign rules)
- `reverses_id` INTEGER NULL REFERENCES goal_allocations(id)
- `created_at` TEXT NOT NULL
- CHECK: exactly one owner. Goal kinds (`sweep`, `withdrawal`) set `goal_id`. Fund kinds (`reserve`, `draw`,
  `opening`) set `line_key`. A `reversal` takes the owner of the row it reverses.
- Sign rules: `sweep` and `reserve` and `opening` are positive. `withdrawal` and `draw` are negative. A
  `reversal` has the opposite sign of its target.
- Indexes: `(goal_id)`, `(line_key, month)`.
- Balance = `SUM(amount)` over the owner's rows. Append-only. No row is ever updated or deleted.

`closed_months` (already has `closed_at`, `leftover_raw`, `leftover_capped`, `sweep_note` from m0002)
- Add `expected_income` REAL, `regular_spend` REAL, `reserve_total` REAL, `shortfall` REAL,
  `swept_total` REAL.
- `leftover_capped` is no longer meaningful (the old "min with budget minus spend" cap is retired). It stays
  NULL. Not dropped (see Q12).

`sweep_rules` (exists from m0001, unchanged)
- Keep `(goal_id, priority_rank, allocation_type, amount)`. The app enforces unique `priority_rank`, percentages
  summing to at most 100, and goal existence.

No backfill. `expense_type='Goal'` has 0 rows, so nothing to carry forward.

## 3. Leftover and fund rules (per month M)

Definitions, computed from the DB (not stored until approval):

- `income` = `effective_expected_income(M)`. If `None`, no proposal: 400 "Set expected income for M first".
- `irregular` lines = budget lines active in M with frequency != Monthly.
- `irregular_spend` = Monthly-type expenses in M whose (category_id, subcategory_id) matches an irregular line
  active in M. A budget line's (category, subcategory) is unique, so classification is unambiguous.
- `regular_spend` = all other Monthly-type expenses in M. This includes overspend on monthly lines and
  unbudgeted spend.
- `reserve_M` = Σ monthly_equivalent(amount, frequency) over irregular lines active in M.
- Fund per line: `available = balance_prev + reserve_line_M`. `draw_line = min(irregular_spend_line, available)`.
  `shortfall_line = irregular_spend_line - draw_line`. Fund balance never goes negative.
- `shortfall` = Σ shortfall_line. It reduces this month's leftover once. It does not carry forward.
- `leftover_raw` = `income - regular_spend - reserve_M - shortfall`. Can be negative.
- `pot` = max(0, leftover_raw). Negative leftover sweeps nothing.

Sweep allocation (per approved month, on `pot`):
1. Eligible goals: `completed = 0`, with at least one rule. Completed goals receive nothing.
2. Fixed rules in ascending `priority_rank`: `grant = min(amount, remaining_pot, goal_need)`, where
   `goal_need = max(0, target_amount - balance)`.
3. Percentage rules: each is `pct% of the post-fixed remainder` (parallel, same base; see Q1), then capped by
   `goal_need` and by the pot still available.
4. Whatever is left is **Unallocated**. It is kept, not rescaled, and no goal receives overflow. A goal that
   hits its target leaves its share Unallocated (AGENTS.md decision; differs from 09-28 §6, which overflowed).

Proposal response (read-only, `GET /api/sweeps/proposal?month=`): `income`, `regular_spend`, `reserve_total`,
`shortfall`, `leftover_raw`, `pot`, `swept_total`, `unallocated`, and per goal `{goal_id, name, rule, amount,
balance, projected_balance}`, plus per fund `{line_key, name, balance_before, reserve, draw, shortfall}`.
No `overfunded` field, because caps by goal need make it impossible.

## 4. Approve and reopen

`POST /api/sweeps/{month}/approve`, body = the accepted proposal (`goal_id` + `amount` pairs; the server recomputes
and rejects a mismatch with 409 so approval is exactly what was shown). One transaction:
- Insert `reserve` rows (one per irregular line), `draw` rows (one per line with `draw > 0`), `sweep` rows (one per
  goal with `amount > 0`).
- Insert or update `closed_months` with the audit fields.
- Errors raise before commit, so a failed request writes nothing.

Guards:
- Month must end before today's month: `M <= previous month`. The current month cannot be swept.
- Months approve in sequence. Approving M requires `M-1` to be closed, or `M` to be the baseline (below).
- Already closed: 409 unless reopened.

`POST /api/sweeps/{month}/reopen`: appends `reversal` rows that cancel that month's `sweep`, `reserve`, and `draw`
rows, then deletes the `closed_months` row (or marks it reopened). Refused if a later month is closed, since
the fund balances after it depend on this month. Append-only, so history stays auditable.

Baseline: the first month the ledger covers. Its `opening` fund rows carry each irregular line's starting balance,
entered by the user (default 0). Before the baseline, nothing is reserved or swept. This matters because m0004
will carry the $6,000 income back to 2025-11, and without a baseline the first sweep would reserve and sweep
history (Q5).

## 5. Goal endpoints and deletes

- `GET /api/goals` gains `balance`, `contributed_this_month`, and `needs_per_month` (derived; see Q8).
- `POST /api/goals/{id}/withdrawals` body `{amount, month, note?}`. Writes a negative `withdrawal` row. 400 if
  amount exceeds balance.
- `DELETE /api/goals/{id}`: 409 if balance is nonzero. `goal_allocations` uses `ON DELETE RESTRICT`, so
  the DB also refuses. Links are still deleted with the goal.
- `goal_budget_links` keeps its table and UI (it is envelope metadata). It no longer feeds any money figure
  (Q9).

## 9. Verification

- Pure math tests: fixed then percentage order, caps by pot and by need, completed goals skipped, percentages
  summing to 100 or less, negative leftover yields zero, shortfall with partial and zero fund.
- Conservation property: `sum(sweep) + unallocated == pot` for random inputs; fund balance never negative;
  `sum(draw) + shortfall == irregular_spend`.
- Ledger: owner CHECK, sign CHECK, reversal restores balances exactly, reopen refused when a later month is closed.
- API: proposal is read-only (no rows written); approve with stale amounts gives 409; double approve gives 409;
  current month refused; out-of-sequence refused; failed approve writes nothing.
- Migration test on a v3-shaped fixture, plus idempotency.
- Backend: `.venv/bin/python -m pytest`. Frontend: `cd web && npx vitest run` and `npm run build`.
- The Planning and Goals UI have not been checked in a running browser. A manual check is needed before commit.

## 10. Open decisions (recommendation in brackets)

1. Percentages: shares of the post-fixed remainder, parallel, sum at most 100. [Recommended.] Or sequential
   (each percentage of what is left)?
2. Caps: fixed and percentage grants are capped by goal need (target minus balance). Anything beyond need stays
   Unallocated. [Recommended.]
3. Irregular spend: Monthly-type expenses under an active irregular line's pair draw from that line's fund. All
   other spend counts as regular. [Recommended.] Confirm this is how you want annual bills recorded.
4. Shortfall: the uncovered part of a bill reduces that month's leftover once. The fund resets at 0. [Recommended.]
   Or should the deficit carry forward and keep reducing later months?
5. Baseline: start the ledger at a baseline month with opening fund balances (default 0). Which month? [Recommended:
   the month you first confirm, so history is not swept.] Or cover earlier months with real opening balances?
6. Reopen: append-only reversal rows. [Recommended.] Or hard delete like the 09-28 plan?
7. Goal delete with balance: block with 409. [Recommended.] Or allow it and forfeit the balance?
8. Withdrawals in Phase 3: a minimal endpoint and button. [Recommended.] Or defer?
9. `goal_budget_links`: stop using it for money now, keep the table and UI until a later contract migration.
   [Recommended.]
10. Sweep UI location: a panel on the Goals page. [Recommended.] Or Planning or Dashboard?
11. Eligible months: any fully ended month, approved in sequence from the baseline. [Recommended.]
12. Audit columns: add the new fields and leave `leftover_capped` NULL. [Recommended.] Or rename it?
