# Sparse versioned budget schema — rewrite of m0003, budget_store, and tests

**Date:** 2026-10-25
**Status:** IMPLEMENTED 2026-10-25 — backend 190 tests, frontend 7, build clean, verify script OK on a copy of the live DB (live DB still at v2, nothing committed)
**Supersedes:** `.posit/assistant/plans/2026-10-03-1410-plan.md` §§2–8 (physical per-month tables).
Its decisions D2 (month defaults to the prior month), D3 (assign-once UUID `line_key`) and D4
(categories created at submit) survive. D1 (physical `budget_YYYY_MM` tables) is replaced.
**Does not touch:** the 09-28 plan's Phases 0–2 (done). Phase 3 (sweep) and the Phase 4 UI are
explicit non-goals here (§12).

## 1. Why, and what was decided

`m0003` is unshipped, `data/budget.db` is at `user_version=2`, and `data/demo_budget.db` is at 0
(read-only check, 2026-10-25). No database anywhere is at v3, so `m0003` can be rewritten in place
with no bridging migration.

The per-month-table model has three costs the design review found: (a) `m0003` pre-materializes ~84
tables, so an edit to October never reaches November/December ("inherit unless edited" is false for
those months); (b) every cross-month read is a dynamic `UNION ALL` and every rename fans out across
all tables; (c) "reuse last month" and "modify" cannot be expressed for many future months without
rewriting many tables.

Decisions (from the 2026-10-24/25 design sessions):

| # | Decision |
|---|---|
| S1 | Sparse versioned model: `budget_lines`, `budget_amounts (effective_month)`, `month_plans`. "Reuse last month" is zero writes. |
| S2 | Amount for month M = the version row with the greatest `effective_month <= M`. A tombstone row (`amount IS NULL`) ends a line. |
| S3 | Periods stay calendar-aligned (no `due_month`). |
| S4 | **`frequency` is fixed on the line; only the most recent frequency is kept** (user choice, 2026-10-25). See §4.4 for what that implies for history. |
| S5 | Edits take an `apply` scope: `forward` (until changed, **the default**), `month`, or `through <month>`. |
| S6 | `month_plans` holds confirmed state and per-month expected income (inherited forward, same scopes). It ships now **including HTTP endpoints** (user choice); no UI. |
| S7 | Before the live DB is migrated, take a snapshot with SQLite's backup API (user choice). |

## 2. Evidence from the live DB (read-only)

62 lineages (distinct `(category_id, subcategory_id)`) over 88 legacy rows; 18 lineages have more
than one row. Findings that shape the design:

- **One lineage changed frequency** (category_id 4 / subcategory_id 41: 2 distinct frequencies).
  With S4 this is the only lineage whose history is reinterpreted (§4.4).
- **A never-active row exists** (category_id 4 / subcategory_id 132: `effective 2026-07-01`,
  `conclusion 2026-06-30`, listed twice). The old predicate never selects it. It must not define a
  lineage's frequency or create a line.
- **Overlapping windows exist** (category_id 8 / subcategory_id 25: `2020-01→2026-01-31` and
  `2020-04→2026-05-31`). The old rule — latest `effective_date` wins, ties by `id` — must be
  reproduced exactly.
- No NULL `category_id` and no blank-subcategory/NULL-id mismatches, so the blank-category edge case
  (§6) is defensive only.
- All frequencies are one of the four known values.

## 3. Schema (DDL lives in `m0003`; no app module owns it)

A shipped migration must not change behavior because a runtime module moved, so `m0003` carries its
own inline DDL and imports nothing from the app. `budget_schema.py` shrinks to a tiny leaf holding
`MONTH_RE` and `is_month` (still used by routers). `table_for`, `month_from_table`, `DISCOVER_SQL`,
`SELECT_COLUMNS`, `create_table_sql` are deleted; **no SQL identifier is ever interpolated again**.

```sql
CREATE TABLE budget_lines (
    id             INTEGER PRIMARY KEY AUTOINCREMENT,   -- stable per line; keeps `budget_id` on the wire
    line_key       TEXT    NOT NULL UNIQUE,             -- uuid4, assigned once (never derived)
    category_id    INTEGER NOT NULL REFERENCES categories(id),
    subcategory_id INTEGER REFERENCES categories(id),   -- NULL = no subcategory
    frequency      TEXT    NOT NULL DEFAULT 'Monthly'
                   CHECK (frequency IN ('Monthly','Quarterly','Bi-annually','Annually')),
    created_at     TEXT    NOT NULL
);
-- One line per (category, subcategory). A line that ended is revived, not duplicated.
CREATE UNIQUE INDEX uq_budget_lines_target
    ON budget_lines (category_id, COALESCE(subcategory_id, 0));

CREATE TABLE budget_amounts (
    line_key        TEXT NOT NULL REFERENCES budget_lines(line_key) ON DELETE CASCADE,
    effective_month TEXT NOT NULL CHECK (effective_month GLOB '[0-9][0-9][0-9][0-9]-[01][0-9]'),
    amount          REAL,                               -- per-period amount; NULL = tombstone (line ends)
    PRIMARY KEY (line_key, effective_month)
) WITHOUT ROWID;

CREATE TABLE month_plans (
    month           TEXT PRIMARY KEY CHECK (month GLOB '[0-9][0-9][0-9][0-9]-[01][0-9]'),
    status          TEXT NOT NULL DEFAULT 'inherited' CHECK (status IN ('inherited','confirmed')),
    confirmed_at    TEXT,
    expected_income REAL                                -- NULL = inherit from the latest earlier explicit value
);
```

Notes:
- Names are **not stored** on the line; they are joined from `categories`. A rename is therefore a
  single `categories` update and `rename_category_strings` is deleted. (This also ends the
  "string diverged from id" dual-write guard for budgets; recategorizing a line changes its ids.)
- `budget_lines` and `budget_amounts` need `PRAGMA foreign_keys=ON` for the cascade; both
  `database.get_db()` and `run_migrations` already set it.
- A row absent from `month_plans` means status `inherited` and no income override.
- The legacy `budgets` and `budget_drafts` tables stay untouched (expand-only), exactly as today.
- No change to `database.init_db()` (the new tables are created by the migration only).

## 4. Semantics (the part that needs to be exactly right)

### 4.1 Resolving a month

```sql
SELECT l.id, l.line_key, l.category_id, l.subcategory_id,
       c.name AS category, COALESCE(s.name,'') AS subcategory,
       a.amount AS limit_amount, l.frequency, a.effective_month AS effective_since
FROM budget_lines l
JOIN categories c ON c.id = l.category_id
LEFT JOIN categories s ON s.id = l.subcategory_id
JOIN budget_amounts a ON a.line_key = l.line_key
 AND a.effective_month = (SELECT MAX(effective_month) FROM budget_amounts
                          WHERE line_key = l.line_key AND effective_month <= :month)
WHERE a.amount IS NOT NULL
ORDER BY c.name, subcategory, l.line_key;
```

Reads never write. A month before a line's first version simply does not contain it; any future
month resolves forward indefinitely. `inherited` (returned by `resolve_view`) now means "this month
is **not confirmed**" (`month_plans.status != 'confirmed'`), not "has no table".

### 4.2 The apply-scope algorithm (one function, used by create/edit/delete)

`_write_version(conn, line_key, month, amount | None, apply, through)` — `None` writes a tombstone.

1. `apply='month'` ⇒ `through = month`. `apply='through'` requires `through >= month`.
   `apply='forward'` ⇒ `through = None`.
2. If `through` is set: `restore_month = shift(through, 1)`; compute `restore` = the effective amount
   (or `None`) **at `restore_month` before any mutation**.
3. Delete explicit rows with `month < effective_month <= through` (the range overrides them).
4. Upsert `(line_key, month, amount)`.
5. If `through` is set and **no explicit row exists at `restore_month`**, write `restore`
   (an amount, or a tombstone if the line was not active there).
6. Normalize the line (§4.3).

`forward` leaves later explicit rows alone, so it means "until the next explicit change".

### 4.3 Normalization and garbage collection

After every write, walk the line's rows ascending and drop any row whose state equals the state
before it (a leading tombstone equals "not yet started"; a repeated amount is redundant). If no rows
remain, delete the line (cascade). Normalization is idempotent and never removes a row that changes
an effective value, so history is preserved.

### 4.4 Frequency (S4) and what it does to history

`frequency` is one value per line. Consequences, all deliberate:

- **Migration:** a lineage's frequency is that of its most recent ever-selected legacy row
  (`max(effective_date, id)`). Earlier rows with a different frequency are **converted so their
  monthly equivalent is preserved**: `amount × divisor(final) / divisor(row)`. Without conversion a
  historical `100/Monthly` would be reread as `100/Annually`. Only one live lineage is affected; the
  verify script prints each converted row (before/after) so you can sanity-check it.
- **Runtime:** `update_line(frequency=…)` rescales every existing version of that line by
  `new_divisor / old_divisor` in the same transaction, then applies the requested amount with the
  requested scope. Past reporting keeps the same monthly-equivalent; it is just expressed in the
  new cadence. (Amounts are stored unrounded; display rounds, as `budget_math` already does.)
- The cadence of a past period is not recoverable after a change. That is the accepted cost of S4.

### 4.5 One line per (category, subcategory)

The unique index enforces what the legacy lineage grouping and the old `_pick_latest` already
assumed. `insert_line`: if a line exists for that pair and is **active** in the target month →
`LineConflict` (HTTP 409); if it exists but is not active there (ended or not yet started) → its
`line_key` is reused and a version is written. Recategorizing onto an occupied pair also raises
`LineConflict`. `line_key` stays assign-once; it is simply not re-minted for a revived line.

## 6. `m0003` rewrite (`backend/migrations/m0003_per_month_budgets.py`)

Keep the filename/`Migration(3, …)` slot; rename the registry label to
`"versioned budgets: budget_lines + budget_amounts + month_plans"`. `LATEST_VERSION` stays 3.

Algorithm (event-based, so it has **no dependency on today's date** and no horizon or
`MAX_SPAN_MONTHS`):

1. `budgets` missing → create the three tables and return. Create tables with `IF NOT EXISTS`.
2. If `budget_lines` already has rows → return. (All-or-nothing inside the runner's transaction; a
   second run via `PRAGMA user_version = 2` is a no-op.)
3. Read legacy rows; validate dates with the existing strictness (ISO `YYYY-MM-DD`, raise on
   malformed). Group by lineage `(category_id, subcategory_id)`. Rows with NULL `category_id`, or a
   non-blank subcategory with NULL id, cannot be represented: skip them, count them, and print one
   warning line (none exist live; the verify script lists any).
4. Per lineage, event months = `{month(effective_date)} ∪ {month(conclusion_date)+1}`. Evaluate the
   **old predicate** at each event month, latest `(effective_date, id)` wins:
   `effective_date <= last_day(M) AND (conclusion_date IS NULL OR conclusion_date >= first_day(M))`.
   State only changes at events, so evaluating there is sufficient.
5. Frequency = the frequency of the ever-selected row with the greatest `(effective_date, id)`.
   Convert each state's amount to that frequency (§4.4) using a divisor table **copied into the
   migration** (not imported). An unknown frequency string is treated as divisor 1 and reported.
6. Emit a version only where the converted amount changes: `None→amount` (start), `amount→amount'`
   (change), `amount→None` (tombstone). A leading `None` emits nothing. A lineage that is never
   active gets no line (the never-active `4/132` row).
7. Insert `budget_lines` (fresh `uuid4`, `created_at`) and its `budget_amounts` rows.

Same lineage grouping and `line_key`-per-lineage rule as before; the only structural change is that
a lineage is one line with sparse versions rather than one row per month.

## 7. HTTP changes

All existing routes keep their paths and response shapes (plus the additions noted).

**`routers/budgets.py`**
- `BudgetCreate` gains `apply: Literal["forward","month","through"] = "forward"` and
  `through: Optional[str]`. `PATCH` and `DELETE` take `apply` / `through` as query params next to
  `month`; `DELETE`'s old `forward` bool is removed (the UI never sent it true).
- Validation → 400: bad month, `through` missing with `apply=through`, `through < month`.
  Not active in month → 404 with **no write having happened**. Pair already active → 409.
- `_public` keeps its fields and adds `effective_since`; `inherited` = month not confirmed.
- `/suggested` unchanged (it only calls `resolve_view` and `shift_month`).
- Remove `ensure_month` calls (they no longer exist).

**`routers/categories.py`** — delete the `rename_category_strings` call and fix the docstring;
`/active` is unchanged.

**New `routers/month_plans.py`** (registered in `main.py`):
- `GET /api/month-plans?start=YYYY-MM&end=YYYY-MM` — status per month in range (≤36), for a future
  status strip. Absent rows report `inherited`.
- `GET /api/month-plans/{month}` — `{month, status, confirmed_at, expected_income, income_set_in}`
  (`expected_income` is the effective value or `null`; `income_set_in` is the month of the explicit
  row that supplies it).
- `POST /api/month-plans/{month}/confirm` — idempotent "Keep as is"; writes nothing to the budget.
- `PUT /api/month-plans/{month}/income` — body `{amount ≥ 0, apply, through}`.

`/api/income` (the single `income_sources` row) is **untouched**. Until Phase 3 retires it, two
income concepts coexist; the Dashboard and Goals pages still read the old one. This is noted in
AGENTS.md so it is not mistaken for a bug.

**Other callers**
- `reporting.py`, `expenses.py`, `import_csv.py`: no code change expected (they call `resolve_view`,
  `months_by_line`, `lines_in_range`, `shift_month`). Their tests are the regression gate.
- `backend/migrate.py` (legacy CSV importer): `migrate_budgets` currently expands rows into month
  tables. Change it to insert the CSV rows into the legacy `budgets` table, run the m0002 backfill
  helpers, then call `m0003.migrate(conn)` — one code path for window→version semantics. Keep the
  "skip if lines already exist" behavior. Confirm the call order in `migrate.main()` while
  implementing.
- **`main.py` lifespan:** if `pending_migrations(conn)` is non-empty and the DB file has existing
  tables, write a snapshot via `sqlite3.Connection.backup` to
  `backups/pre_migration_v{from}_to_v{to}_{stamp}.db` before `run_migrations`. Factor the copy into
  one helper in `database.py` and also use it in `POST /api/backup`, replacing `shutil.copy2`
  (which can miss WAL pages — the same reason AGENTS.md mandates the backup API).

## 9. Tests

Backend suite today: 67 passing. The month-table assertions below are rewritten; nothing is
deleted without a replacement.

**`tests/test_budget_store.py` (new)** — unit tests on an in-memory/temp DB after `run_migrations`:
- resolution: before first version → absent; after → effective; tombstone ends; revive after a gap
- read never writes (row counts of all three tables unchanged across `resolve_view`)
- scopes: `month` leaves M−1 and M+1 untouched; `through` restores the prior value at `through+1`,
  overwrites intermediate explicit rows, and keeps an explicit row already at `through+1`;
  `forward` stops at the next explicit change
- delete with each scope; deleting then re-adding the same pair reuses the `line_key`
- conflicts: active duplicate pair → `LineConflict`; recategorize onto an occupied pair → conflict
- normalization: redundant rows dropped, idempotent; line with no rows is garbage-collected
- frequency change rescales all versions and preserves monthly equivalents
- rename is visible instantly through the join (`categories` update only)
- month validation rejects malformed months (the old injection guard, now for values not identifiers)
- plans: `confirm_month` flips only that month, keeps first `confirmed_at`, writes no budget rows;
  expected income inheritance, `month`/`through`/`forward` scopes
- **model-based test:** apply a few hundred random create/edit/delete operations (seeded RNG, an
  explicit integer seed chosen at implementation time) to the store and to a naive dense
  `dict[(line, month)] → amount` model over 36 months; assert identical views after every step.
  This is the strongest guard on §4.2.

**`tests/test_migrations.py`** — `TestMigration3` rewritten; runner/m0001/m0002 tests untouched
(`test_contract_version_is_three`, `[1, 2, 3]` assertions stay valid):
- creates `budget_lines`, `budget_amounts`, `month_plans`, the unique index; **no** `budget_YYYY_MM`
  tables
- equivalence with an independently written legacy predicate for every month from the earliest
  effective month to 6 months past the last event — the test must not call migration helpers
- one `line_key` per lineage; distinct lineages get distinct keys; keys survive a limit change
- a conclusion yields a tombstone at `conclusion month + 1`; a mid-month conclusion keeps that month
- gap then restart in one lineage → tombstone then new version, same key
- overlapping windows: latest `effective_date` wins; inverted window (`eff > concl`) creates no line
- frequency change within a lineage: final frequency kept, earlier amount converted
  (e.g. `100/Monthly` then `1200/Annually` → both versions in Annually terms, 1200 each)
- idempotency: reset `user_version` to 2 and re-run → identical rows
- rows skipped for NULL ids are counted and warned about
- legacy `budgets` and `budget_drafts` left intact (existing assertion kept)
- result is date-independent (the old test pinned `months[-1] == today`; that fragility goes away)

**`tests/test_reporting_partition.py`** — only the `_insert` helper changes (`insert_line(…,
start, apply="through", through=end)`); every assertion should pass unchanged, which is the
regression proof for `months_by_line` and the accrual clamp.

**`tests/test_categories.py`** — five touch points: `table_exists(…)` → "no rows written" checks;
`budget_2025_03` raw SQL → store reads; `list_months(conn) == []` → "no `budget_lines` rows";

`test_migrate_script_stamps_category_ids` → assert lines/versions and the single carried `line_key`.

**`tests/test_budgets_api.py` (new)** — `GET` inherits without writing; `POST`/`PATCH`/`DELETE` with
each `apply` mode; a `PATCH` or `DELETE` of an unknown or inactive line returns 404 **and leaves all
three tables unchanged** (the old defect, now a regression test); 409 on a duplicate pair; 400 on bad
`through`; `inherited` flips after `confirm`.

**`tests/test_month_plans_api.py` (new)** — range endpoint defaults, confirm idempotency, income
scopes, validation errors.

**`tests/test_backup.py` (new, small)** — the snapshot helper produces a readable copy containing
rows written in WAL mode, and is skipped for an empty database. (The lifespan itself is not
exercised: the existing tests use `TestClient(app)` without a context manager.)

**Frontend:** `cd web && npm test` and `npm run build`; one added vitest case if the banner copy has
a testable branch, otherwise just the existing 7 tests.

## 14. Risks and calls I made that you may want to veto

| Call | Why | Cost if wrong |
|---|---|---|
| Convert earlier-frequency amounts to preserve monthly equivalent (S4) | The alternative rereads `100/Monthly` as `100/Annually` | One live lineage; verify script shows it. Easy to flip to "keep raw" before running. |
| Frequency edits at runtime rescale all versions | Keeps history numerically consistent | Surprising if you expected an edit to touch only future months. |
| One line per (category, subcategory), revive instead of duplicate | Matches how the legacy data and reporting already treat lineages | Cannot budget the same pair twice at once; returns 409. |
| `inherited` now means "not confirmed" | Needed for the turnover prompt; table existence never could say | The existing banner fires for any unconfirmed month, including ones you have edited. Fine until the status strip exists. |
| Default scope `forward` | Your choice; matches today's "later months inherit" | A casual edit now reaches later months until the next explicit change. Banner copy states it. |
| Lines with NULL category ids are skipped with a warning | They cannot satisfy `NOT NULL category_id` | None live; verify script would list them. |
| Garbage-collect a line that ends up with no rows | Keeps the table tidy | Only reachable when the line never had an active month, so no history is lost. |
