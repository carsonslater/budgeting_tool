## 3. Design

### 3.1 Suggestions (Planning)

- New `web/src/components/planning/SuggestionsPanel.tsx`. It lists the month's suggestions: category,
  subcategory, frequency, current monthly equivalent, last complete month's spend, hasty and conservative. Each
  row has Apply hasty and Apply conservative. Nothing is applied automatically.
- Apply converts the monthly figure to an amount per period: `amount = monthly × FREQUENCY_DIVISORS[frequency]`,
  rounded to cents. The helper goes in `web/src/lib/budgetMath.ts` (`periodAmountFromMonthly`). It is the inverse
  of `monthlyEquivalent`, which only rounds, so the round trip is exact to the cent.
- Apply calls `updateBudget` with the existing apply scope. Frequency is unchanged. The `budgetKeys.all`
  invalidation refreshes the suggestions too.
- Non-monthly lines are handled per decision D1.

### 3.2 Opening balances and baseline (Phase 3 gap)

- Baseline: a single month, `sweep_baseline`, that is the first month the ledger covers. Before it, no
  reserves, draws, sweeps or prompts occur. Storage is decision D5. Recommended: m0007 creates
  `app_settings(key TEXT PRIMARY KEY, value TEXT)` and inserts `sweep_baseline`. The migration is append-only
  and the pinned-version tests move to 7 (`tests/test_migrations.py`, `tests/test_backup.py`).
- Enforcement, in `compute_proposal` and `approve`: a month before the baseline is refused (400). The baseline
  can be set once, and it cannot move after any close (409).
- Opening rows: `goal_allocations` `kind='opening'`, positive, `line_key` owner, dated at the baseline (D2).
  Writes go through `goal_ledger.add_opening`, which the router exposes as `POST /api/sweeps/openings`.
  `{line_key, amount}` is accepted only while no month is closed. Edits before any close append a reversal
  and a new opening row. Amount 0 is allowed.
- `fund_balance_before` sums rows dated before M. The implementation must confirm an opening dated at the baseline
  counts for the baseline's successor and later months, and that the baseline month itself is not reserved.

### 3.3 Turnover modal (blocking, on app load)

- Backend: `GET /api/turnover` (read-only) returns the target month (the month before today), the baseline,
  `needs_turnover`, and the status of its three steps: `confirmed`, `swept`, and proposal `approvable` with
  `blocked_reason`. It is computed in the backend so the boot logic cannot drift from the store.
- Frontend: `web/src/components/turnover/TurnoverModal.tsx`, mounted at the app root. It opens when
  `needs_turnover` is true. Three steps:
  1. Confirm budget: show the target month's line count and monthly total. "Keep as is" confirms.
  2. Review leftover: income, regular spend, reserve, shortfall, pot, the per-fund table, and the goal split.
  3. Approve sweep: posts the displayed amounts. A 409 reloads the proposal.
- The modal does not close on Escape or on an overlay click. Exit is by completing the steps (D3).
- First run, when no baseline exists: the modal asks for the first month to turn over and the opening balance of
  each irregular line, then sets the baseline (D4). Months before the baseline never prompt.
- Turnover does not run before the baseline is set, so existing history is never prompted.

## 7. Open decisions (recommendation in brackets)

- D1. Non-monthly lines in suggestions. The WMA reads the last three months of actual spend. An annual bill is a
  one-month spike, so the suggestion would be built from a spike and would misstate the monthly reserve.
  [Recommended: exclude non-monthly lines from suggestions. Alternative: base them on a trailing 12-month
  average, which needs a separate calculation and a backend change.]
- D2. Opening balance date. [Recommended: the baseline month itself. Alternative: the month before it.]
- D3. Turnover modal exit. [Recommended: strictly blocking, as AGENTS.md records. Alternative: a "Later this session"
  control that suppresses it until the next app start.]
- D4. First-run baseline. [Recommended: the user picks the first month to turn over. The default is the month
  before today, with opening balances entered at that month. Earlier months never prompt.]
- D5. Baseline storage. [Recommended: m0007 `app_settings` key-value table. Alternative: a dedicated
  `sweep_baseline` table with one row.]
- D6. Conflicting specs. The 09-28 plan §7 calls for a non-blocking banner. The 10-25 plan and AGENTS.md call for a
  blocking modal. This plan follows the modal. [Confirm.]
- D7. The 09-28 plan. [Recommended: leave it in place. This plan supersedes §7, and AGENTS.md notes which one applies.]
