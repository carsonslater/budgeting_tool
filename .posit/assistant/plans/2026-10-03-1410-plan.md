## 2. Cost of physical tables (acknowledged)

Physical tables are materially harder than one `month` column. Accepted consciously:

1. **Cross-month queries become dynamic `UNION ALL`** over tables discovered from `sqlite_master`.
   Today [reporting.py:130](../backend/routers/reporting.py) and
   [budgets.py:85](../backend/routers/budgets.py) are plain windowed selects.
2. **`SELECT DISTINCT subcategory FROM budgets`** ([expenses.py:82](../backend/routers/expenses.py),
   [import_csv.py:259](../backend/routers/import_csv.py)) becomes a union; its scope must be
   pinned (recommend trailing 12 months).
3. **Migrations loop over N tables.** A future column change to budget rows is N `ALTER TABLE`s.
4. **Test fixtures lose their static DDL.** `BASELINE_DDL` in
   [test_migrations.py](../tests/test_migrations.py) is a string; per-month tables are created at
   runtime.

**Containment:** a single module owns naming, discovery, creation and query-building (§6). Routers
never name a table. This keeps the layout one module's concern.

Not a problem: FK to the static `categories` table still works; SQLite DDL is transactional, so
migration-created tables roll back correctly.

## 3. Schema and naming

```python
# backend/budget_store.py
_MONTH_RE = re.compile(r"^\d{4}-(0[1-9]|1[0-2])$")   # strict; table names are interpolated

def table_for(month: str) -> str:                      # '2026-10' -> 'budget_2026_10'
    ...
```

Per-table DDL (created `IF NOT EXISTS`):

```sql
CREATE TABLE IF NOT EXISTS budget_2026_10 (
    id             INTEGER PRIMARY KEY AUTOINCREMENT,
    category_id    INTEGER REFERENCES categories(id),
    subcategory_id INTEGER REFERENCES categories(id),
    category       TEXT    NOT NULL,          -- legacy string during expand
    subcategory    TEXT    NOT NULL DEFAULT '',
    limit_amount   REAL    NOT NULL DEFAULT 0,
    frequency      TEXT    NOT NULL DEFAULT 'Monthly',
    line_key       TEXT    NOT NULL,          -- §4
    created_at     TEXT,
    UNIQUE(line_key)                          -- one row per line per month
);
```

The month is the table name, so no `month` column and no
`effective_date`/`conclusion_date` — those concepts disappear. `UNIQUE(line_key)` is the
per-month uniqueness the window predicate used to provide, now enforced directly. The month is
validated against `_MONTH_RE` **before** interpolation; table names are the only place SQL is
built by string.

**Discovery:**

```sql
SELECT name FROM sqlite_master
WHERE type = 'table' AND name GLOB 'budget_[0-9][0-9][0-9][0-9]_[0-9][0-9]'
```

## 4. UUID line identity

- `line_key` is a **`uuid4` generated once** at line creation and carried forward, stored as TEXT.
- It is *not* derived from live values. A key hashed from the category name breaks on rename; one
  derived from `(category_id, subcategory_id)` breaks on reclassification. Assign-once survives
  both.
- Carried forward at materialization (§5) and across any split/edit of the same line.
- A new line gets a fresh `uuid4`.

## 5. Materialization and carry-forward

- Month M's table is seeded from M-1's lines, **preserving each `line_key`**.
- **Creation is lazy, on first write to M** — *not* on read. The current
  [get_drafts_for_month](../backend/routers/budget_drafts.py) inserts on a `GET`; that defect (F7)
  must not be reproduced.
- Editing M touches only M's table. Independence is physical, not derived.
- Future months are not rewritten, so the old commit-cascade (F8) cannot recur.

## 8. Migration v3

1. Register `Migration(3, "per-month budget tables + line_key", _m0003)`.
2. Create the `budget_store` helpers first (migrations import from it).
3. For each existing `budgets` row, expand its `[effective_date, conclusion_date]` window into
   monthly rows, bounded by a horizon (open question §11.1).
4. Assign one `uuid4` per legacy lineage — grouped by `(category_id, subcategory_id)` — shared
   across that lineage's expanded rows.
5. **Expand only:** leave `budgets` in place and populated until every read path is switched.
6. Update `LATEST_VERSION` assertions in [test_migrations.py](../tests/test_migrations.py)
   (`test_contract_version_is_two`, `test_applies_every_version_from_zero`).

## 9. Interactions with the existing plan

- **`budget_drafts` is retired** — its `target_month` role is subsumed. This replaces 09-28 §7.
- **The 8 `goals.py` budget sites shrink**: 09-28 Phase 3 already deletes the
  `goal_budget_links` synthetic-budget-row behavior, so those sites disappear rather than migrate.
- **Phase 1 must be re-expressed.** A non-monthly line appears in every month it spans; accrual
  reporting becomes an aggregation over those rows rather than a windowed read.

## 10. Verification

- `table_for` rejects malformed months (injection guard) before any DDL.
- Migration v3: idempotency; a line effective 2025-01-01→2025-03-31 yields exactly 3 monthly
  rows sharing one `line_key`.
- `UNIQUE(line_key)` rejects a duplicate line-month.
- Editing month M leaves M-1 and M+1 byte-identical.
- `lines_in_range` returns the same aggregate as the old windowed `SELECT`.
- Renaming a category via `PATCH /api/categories/{id}` leaves `line_key` grouping intact.
- `cd web && npm run build` clean; a category typed while planning M appears in M's suggestions.
